## 为什么需要它

Emacs 从来不缺 Markdown 的编辑模式，但「把一份文档渲染成好看的样子」一直是个
被反复重新发明的问题：不同的包各自带一套字体锁定规则，代码块、表格、脚注、
图片的处理互不相同，换一个包就换一种观感。与此同时，Emacs 作为编辑器最擅长
的三件事——原生滚动、isearch、窗口切分——在许多「预览」实现里反而被绕开了，
它们要么把文档塞进一个自绘的画布，要么只显示当前窗口能看到的那一屏。

ETAF Markdown Preview 想做的事情很具体：**把 Markdown 当成一个真正的文本应用
来渲染**。它复用 ETAF 的组件目录与 Ebox 的排版引擎，把整篇文档发布进一个普通
的 Emacs buffer，然后让 Emacs 自己负责滚动、搜索与窗口。文档是只读的，渲染是
一次性的，窗口大小变化只需要重新排版——不需要交互、不需要网络、也不需要重新
解析。换句话说，它是一台「静态渲染器」，而不是又一个有自己状态机的编辑器。

这份手册本身就是这个项目的真实文档，同时也是它的展示样例。你现在看到的每一个
标题、段落、列表、表格、代码块、提示块、图片与脚注，都来自普通 Markdown 源
文件，没有为演示而定制任何语法。

> [!NOTE]
> 本手册使用 etaf-md-preview 自身渲染。按 `r` 可以重新读取源文件并按 `t` 可
> 以在深色、浅色与纸色三套主题之间切换。

## 快速开始

### 环境要求

这个包只依赖工作区里已经存在的框架包，没有额外的第三方依赖。视频封面与终端
下的图片转换是可选的：没有它们，图片退化为占位卡片，视频只保留可打开的链接。

| 依赖 | 用途 | 必需 | 检查方式 | 备注 |
|:-----|:-----|:----:|:---------|-----:|
| Emacs 29.1+ | ETAF 运行时与内置的图片支持 | ✅ | `emacs --version` | 推荐 30 以上 |
| ETAF | 组件、状态与应用运行时 | ✅ | `(require 'etaf)` | `0.2.1` 起 |
| ETAF UI | 按钮、标签、分割线等共享控件 | ✅ | `(require 'etaf-ui)` | `0.1.0` 起 |
| Ebox | 排版、绘制与增量发布 | ✅ | `(require 'ebox)` | `3.0.0` 起 |
| ECSS | 选择器与层叠计算 | ✅ | `(require 'ecss)` | 随 Ebox 加载 |
| ffmpeg | 视频封面帧与终端图片转换 | 🔵 | `ffmpeg -version` | 缺失时降级 |

### 安装

把仓库与框架包放在同一级目录，然后依次把它们的根目录加入 `load-path`。包的
入口只做一件事：注册公共 API 并把实现目录加进 `load-path`，所以只要根目录
可达，`require` 就能找到它。

```elisp
(add-to-list 'load-path "/path/to/emacs-taf/ecss")
(add-to-list 'load-path "/path/to/emacs-taf/ebox")
(add-to-list 'load-path "/path/to/emacs-taf/etaf-ui")
(add-to-list 'load-path "/path/to/emacs-taf/etaf")
(add-to-list 'load-path "/path/to/emacs-taf/etaf-apps/etaf-md-preview")
(require 'etaf-md-preview)
```

对于用 `package.el` 安装的归档，只需要把包根目录加入 `load-path`；入口
Commentary 里记录的是唯一权威的公共接口清单，动手扩展之前先读它。日常开发
则必须把工作区里的框架源码也挂进来，否则量到的行为与仓库当前状态不符。

```bash
make -C /path/to/emacs-taf/etaf-apps/etaf-md-preview check
make -C /path/to/emacs-taf/etaf-apps/etaf-md-preview benchmark
```

### 第一次预览

打开预览只有一条命令。它接受文件路径，也会读取当前 buffer 的 Markdown 文件
作为默认值；同一个文件已经有预览 buffer 时，会直接切换到那个 buffer，而不是
重复渲染第二份。

```
M-x etaf-md-preview-open RET README.md RET
```

> [!TIP]
> 把 `etaf-md-preview-open` 绑定到你习惯的键上会顺手得多，比如
> `(keymap-global-set "C-c m" #'etaf-md-preview-open)`。

## 使用指南

### 键盘操作

预览 buffer 保留全部原生阅读习惯：isearch、`occur`、窗口切分、标记与段落移动
都没有被覆盖。落在预览键位表里的按键只有下面这些，它们都是「导航与展示」级别
的操作，不会改变文档内容。

| 按键 | 行为 | 说明 |
|:-----|:-----|:-----|
| `n` / `p` | 跳到下一个 / 上一个标题 | 按大纲顺序 |
| `TAB` | 从补全列表里选一个标题 | 同时也接 `imenu` |
| `RET` / 鼠标左键 | 打开光标下的链接、图片或视频 | 文档内锚点直接跳转 |
| `r` | 重新读取并重绘 | 源文件改动后使用 |
| `t` | 在深色、浅色、纸色之间循环 | 共享组件同步换色 |
| `[` / `]` | 收窄 / 放宽阅读栏 | 每次四列 |
| `?` | 显示一行键位摘要 | 不覆盖其他 buffer |
| `q` | 卸载预览并关闭 buffer | 释放运行时 |

### 大纲导航

整篇文档发布成一个普通 buffer，因此「跳到某个标题」不是自绘画布里的滚动偏移
计算，而是一次实实在在的 buffer 搜索。预览器在解析时给每个标题生成稳定锚点，
导航时按文档顺序匹配渲染出来的标题文本，所以重名标题也能按出现次序落点。

- 大纲索引从零开始，`etaf-md-preview-locate` 接受的是索引而不是标题文本；
- `etaf-md-preview-outline` 返回 `(级别 文本 锚点)` 三元组，脚本可以直接
  消费；
- 标题锚点参与文档内跳转，`#功能矩阵` 这样的链接会落到对应标题；
- 移动窗口后再导航不需要重新挂载，位置是每次按需计算的。

### 主题与排版

阅读栏有最大宽度，窄窗口下自动收缩，窗口变化后重新排版；`[` 与 `]` 可以手工
微调。三套调色板共享同一套布局，主题令牌会发布给整个预览子树，所以 ETAF UI
的共享控件（标签、分割线、按钮）会跟着一起换色，而不会出现一半深色一半浅色
的断裂。

> [!IMPORTANT]
> 预览是只读的。Ebox 发布时会把 buffer 设为只读，避免输入内容在下一次重绘
> 时被悄悄覆盖；要修改文档，请回到源文件。

## 支持的 Markdown 语法

下面按类别说明支持范围。默认方言是 **GFM 扩展集**：CommonMark 核心加上表格、
任务列表、删除线、裸链接与脚注，再加 front matter 与提示块这两个文档约定。
解析器内部是同一棵语义树，方言差异只是识别器开关，所以 `~~x~~` 这类写法在
`commonmark` 方言下会原样保留，而不是渲染失败。

### 标题层级

标题使用字体、字重与颜色表达层级，一、二级标题额外带一条分隔线；锚点由标题
文本生成，重复标题自动加序号。这样一个真实的文档可以放心地使用六级标题，
而不会出现两个同名锚点互相覆盖。

### 行内样式与链接

行内内容由若干样式连续的文字段组成，同一段落里的强调、代码与链接各自生效，
换行仍然按整段宽度处理，不会在样式边界上被切成两块。除了常见写法，还支持
`***粗斜体***`、删除线 ~~像这样~~、行内代码 ``含反引号的 ` 代码``，以及
[带标题的行内链接](https://example.com "示例站点")、[参考式链接][manual]、
[文档内跳转](#功能矩阵)、自动链接 <https://www.gnu.org/software/emacs/>、
裸链接 https://github.com 与邮箱地址 <dev@example.com>。

转义与实体同样被识别：`\*不是斜体\*`、`` \`不是代码\` ``、&copy; 2026
&mdash; 保留所有权利&hellip;。行尾输入两个空格会得到一次硬换行：  
这一行是新行的开始，而不是被当作软换行接在上一段末尾。

### 引用与提示块

普通引用保留左侧强调条与浅色背景，可以嵌套，也可以包含列表、代码等块级内容。
识别五种提示块：`[!NOTE]`、`[!TIP]`、`[!IMPORTANT]`、`[!WARNING]` 与
`[!CAUTION]`；每种都有自己的图标、标题与配色，未启用扩展时它们退化为普通
引用。

> 引用可以承载一整段解释性文字，也可以包含列表：
>
> - 引用中的有序步骤
> - 引用中的无序要点
>
> > 嵌套的引用继续缩进，左边界由强调条表达。

> [!NOTE]
> 提示块的内容与普通引用一致，只是外观不同；标题行由解析器从标记里剥离，
> 不会出现在正文中。

> [!TIP]
> 在源文件里改完文档后按 `r`，解析、渲染与发布一次完成，不需要重启 Emacs。

> [!IMPORTANT]
> 文档内跳转依赖标题锚点；重复标题会自动编号，因此两个「常见问题」小节
> 都可以被正确链接到。

> [!WARNING]
> 行内编辑尚未支持输入法组合输入。需要编辑时请回到源 buffer，预览只负责
> 呈现。

> [!CAUTION]
> 源文件被删除后按 `r` 会保留最后一次成功渲染的内容，并在状态里记录失败
> 原因，不会把预览清空。

### 代码与缩进块

围栏代码块显示语言标签，长行按字符折行，块内四周留出空白，不会紧贴边框。
缩进四格的代码块同样被识别；两者在渲染上没有区别，只影响源文件的写法。

```elisp
(defun etaf-md-preview-open (source)
  "Open SOURCE, a file path or a session, as a rendered preview."
  (interactive (list (read-file-name "Markdown file: " nil nil t)))
  (let* ((session (if (listp source)
                      source
                    (etaf-md-preview-create :file source)))
         (buffer (etaf-md-preview-open session)))
    (with-current-buffer buffer (goto-char (point-min)))
    buffer))
```

### 脚注

脚注引用按出现顺序编号，定义统一收集在文档末尾；同一脚注可以被多处引用，
激活引用会跳到对应定义。定义中可以使用任何行内语法[^design]，包括
`代码`、**强调**与[链接][dots]。这是文档级状态[^etaf]，脚注编号不会因为
渲染次数变化而漂移。

[^design]: 设计决策记录在[项目手册][manual]与[架构说明][docs-arch]里，
    包含方言边界与渲染取舍。

[^etaf]: ETAF 是 Emacs Text Application Framework 的缩写，也是这个预览器
    的底层应用运行时。

[^dots]: 这里是第三个脚注，用来说明多个定义可以连续排列而不影响正文排版。

### 分割线与实体

分割线用于在长文档里切换话题：

---

字符实体在正文与代码里都按字面处理：`&amp;`、`&lt;`、`&gt;` 渲染为
`&`、`<`、`>`；中文排版常用的 &mdash;、&hellip;、&copy; 也直接支持。

## 架构说明

预览器把「文档」与「展示」分开：解析器是一个纯函数，输入文本、输出语义
树；模型持有会话状态，并把主题、宽度与错误作为响应式来源；视图层把语义树
映射为 ETAF 节点；应用层只负责 buffer、键位与生命周期。四层之间没有反向
依赖，所以脚本可以只加载模型做批处理，测试可以只挂载视图检查输出。

渲染路径只有一条：`etaf-md-preview-view` 返回普通 ETAF 视图，`etaf-mount`
把它交给 ETAF，ETAF 再降级成 Ebox 的规范输入，由 Ebox 完成测量、排版与
发布。预览器从不直接调用 Ebox，也不在 buffer 里写文本；这样做的好处是所有
增量发布、失败回滚与只读保护都自动继承，而应用代码只有几百行。

> 详细的数据流、模块职责与渲染决策见[架构说明][docs-arch]；
> 每个公共函数的行为与错误语义见[项目手册][manual]。

## 性能与验证

静态文档的性能目标很明确：**窗口尺寸变化不应触发重新解析，也不应触发整篇
重绘**。宽度是布局输入而不是文档内容，Ebox 在窗口变化后重新排版，应用层只
在阅读栏宽度的档位真正变化时更新一次状态。

验证分三层：批处理验收覆盖解析、渲染、导航与媒体降级；GUI 探针检查帧级
不变量（没有超宽的行、存在可交互链接、大纲非空）；基准脚本对一个确定性的
大文档记录解析、挂载与刷新耗时，用来和上一次结果比较。

| 场景 | 计时边界 | 目标 |
|:-----|:---------|-----:|
| 解析 | 文本进入解析器到语义树返回 | 与文档尺寸线性 |
| 挂载 | 视图构建到首次发布完成 | 与可见内容相关 |
| 导航 | 按键到光标落点 | 与文档尺寸无关 |
| 窗口变化 | 重新排版到画面刷新 | 视口量级，不重解析 |

## 开发与发布

开发循环很短：改代码、跑 `make check`、在真实的图形帧里看一眼，然后提交。
提交信息遵循 Conventional Commits，改动在同一仓库里完成，检查在提交前跑完。
发布走 Jujutsu 的工作流：先检查将要发布的提交范围，再把 `main` 书签推到
远端。

- 修改解析器：先加失败用例，再改识别规则，最后回归整套验收；
- 修改视图层：在 GUI 探针里确认行宽、行高与边框留白；
- 修改模型：确认无 buffer 的会话仍然可用，`state` 快照保持可序列化；
- 发布前：`make check` 全绿，工作区检查通过，提交信息通过格式门禁。

> [!TIP]
> `make benchmark` 会生成一个固定结构的大文档并打印解析、挂载与刷新耗时。
> 修改渲染路径前后各跑一次，就能看出改动是否引入了回退。

## 常见问题

### 为什么按 `q` 之后重新打开要重新渲染？

关闭预览会卸载运行时并释放 buffer，这是刻意的：一个会话的生命周期绑定到它
显示出来的那份运行时上，重复挂载保留中间状态反而让失败恢复变得含糊。重新
打开的成本主要在一次解析与一次发布，文档越大越应该让这一步保持无状态。

### 为什么图片变成了点阵而不是原图？

当前帧没有可用的图形支持，Ebox 按契约回退到终端转换器；安装了 ffmpeg 之后
终端下会使用半块字符渲染，仍然是彩色可辨认的。要在终端里获得更好的效果，
可以同时安装 chafa。

### 为什么表格在某些终端下边框看起来是断的？

Ebox 用绘制区块表达边框，终端字体如果没有对应的制表符字形，会以替代字符
显示。切换到带完整 Unicode 字形的等宽字体即可。
